# ♠ 텍사스 홀덤

AI 상대와 혼자 즐기는 노리밋 텍사스 홀덤.
빌드 도구도, 외부 의존성도 없습니다. `index.html` 을 브라우저로 열면 바로 시작됩니다.

```bash
open index.html            # macOS
xdg-open index.html        # Linux

npm start                  # 또는 로컬 서버 (http://localhost:8000)
```

로컬 서버로 열면 오프라인 설치(PWA)와 Web Worker 가 함께 켜집니다.
`file://` 로 열어도 워커는 Blob URL 로 동작합니다.

---

## 무엇이 다른가

무료 홀덤 앱은 많지만 대부분 봇이 약합니다. 이 프로젝트는 **봇이 실제로 강한 것**과
**플레이어의 실력이 느는 것**, 두 가지를 목표로 만들었습니다.

### 봇이 실제로 강하다

봇은 매 결정마다 상대의 액션에서 **레인지를 역산**하고, 그 레인지로만 승률을
시뮬레이션합니다. "상대는 무작위 홀카드"라는 흔한 가정은 실측 결과 최대 **23.8%p**
까지 틀립니다(포켓 99: 랜덤 상대 72.8% vs 상위 15% 레인지 49.3%).

| 측정 | 초기 구현 | 현재 |
|---|---|---|
| 고정 규칙 TAG 봇 상대 손익 (4인 고급, 20시드 × 1000핸드) | **-149 bb/100** | **+15 bb/100** |
| 같은 측정, 9인 풀링 (고급, 30시드 × 500핸드) | — | **+5 bb/100** |

상대 성향 5종 전부에게 이깁니다 (고급, bb/100, 표준오차 4인 ±3~14 · 9인 ±2~9):

| 상대 | 4인 (20시드 × 1000핸드) | 9인 (30시드 × 500핸드) |
|---|---|---|
| TAG (타이트-어그레시브) | +15 | +5 |
| LAG (루즈-어그레시브) | +41 | +38 |
| 콜링스테이션 | +260 | +260 |
| 락 (프리미엄만) | +11 | +6 |
| 밸런스드 (솔버 프리플랍 + 양극 포스트플랍) | +49 | +28 |
| 헤즈업 (2인, 20시드 × 1000핸드) | TAG +25 · LAG +58 · 스테이션 +238 · 락 +40 · 밸런스드 +44 | |
| 봇 VPIP / PFR | 48~58% / 0~8% (루즈-패시브 림퍼) | 30% / 18% (AF 2.2) |
| 핸드 평가기 처리량 | 47,000 회/초 | **288만 회/초** |
| 결정 1회 비용 | 29~69ms (UI 정지) | 0.4~1.3ms (+ 워커) |

상대 봇은 `test/tag-bot.js` 에 고정 규칙으로 다섯 종류가 있습니다 — TAG(기본) · LAG(넓게 열고
3벳·C벳·배럴·블러프 레이즈) · 콜링스테이션(넓게 콜, 안 접음) · 락(프리미엄만) · 밸런스드(솔버 표
프리플랍 + 양극 포스트플랍). `npm run bench` 가 6시드 × 1000핸드로 평균과 표준오차(약 ±6~9
bb/100)를 내고, 마지막 인자로 상대를 고릅니다(`node test/bench.js hard 6 1000 4 lag,station`). `npm run bench:9` 는 같은 측정을 9인 풀링에서
합니다.

9인 튜닝 기록 (30시드 × 500핸드, 고급, 표준오차 약 ±2.5). 효과 없던 것도 적어 둡니다 —
같은 가설을 다시 시험하지 않도록.

| 가설 | 결과 |
|---|---|
| 풀링 오픈 사이즈 2.2 → 2.5bb (작은 오픈이 멀티웨이를 부른다) | 단독으로는 효과 없음 (+1.5 → -1.4) |
| 위 + 오픈에 이미 콜러가 있으면 콜 기준을 콜러당 12% 축소 | **채택** (+1.5 → +5.9, 4인도 +7.8 → +11.9) |

| 콜당했을 때의 승률을 기대 콜러 수만큼의 상대로만 계산 | 4인 +7, 9인 -8 — 상대 전원 기준의 보수적 추정이 낫다 |

| 풀링 앞자리 오픈 레인지를 더 타이트하게 (UTG 11% 등) | 미미 (+1.6), 채택 안 함 |
| 콜러가 있는 팟에서 블러프 3벳 금지 | 그런 자리가 드물어 변화 없음 |
| 멀티스트리트 룩어헤드 v1 — 다음 카드 10장 표본마다 상대 레인지보다 앞서는 비율을 평가해 후속 정책(밸류 추출·체크폴드·쇼다운)으로 기대 팟 산출 (4인 고급 10시드) | 나빠짐 (+9.0 → -5.3), 보수적 변형도 +0.6~+9.2 로 넘지 못함 |
| 룩어헤드 v2 — 다음 카드마다 상대 레인지를 벳 레인지(상위 33%)와 체크 레인지로 나눠 "상대가 벳하면 콜할 가치 / 체크하면 내가 뽑을 가치"를 계산 | 넘지 못함 (+2.2~+7.2). 코드는 `TUNE.lookahead` 뒤에 남김 |
| 프리플랍 솔버 테이블로 결정 (4인 고급 10시드) | 나빠짐 (+9.0 → -10.6, 9인 30시드 +5.1 → -7.7). 오픈에 콜하는 비율 8.5 → 12.3%, 플랍에서 접는 손실 -13.7 → -49.5 bb/100 |
| 솔버를 낮은 실현율(OOP 0.75 / 0.68 / 0.60)로 다시 풀어 결정 | 같음 (-12 / -11 / -10) — 실현율을 낮추면 블라인드 디펜스가 줄고 대신 오픈이 넓어진다 |
| 솔버 빈도를 상대 레인지 역산의 가중치로만 (4인 20시드 · 9인 30시드) | 4인 중립 (+3.0 → +1.3), 9인 나빠짐 (+5.1 → -3.8). `TUNE.solverRanges` 뒤에 남김 |
| **리버스 임플라이드 오즈(rio 1.0) 이후 솔버 재측정** (4인 20시드 · 9인 30시드) | 결정: 4인 +14.9 → -0.0, 9인 +5.2 → +0.4. 역산만: 4인 +8.2, 9인 +5.7. 둘 다: -6.8 / +3.1. 포스트플랍이 나아져도 솔버 프리플랍은 이 상대에게 손해 — 둘 다 계속 꺼 둔다 |
| **상대 5종 매트릭스** (4인 고급 20시드 × 1000핸드): 기본 / 솔버 결정 / 솔버 역산 | TAG +15 / 0 / +8 · LAG +50 / +57 / +45 · 스테이션 +235 / +236 / +277 · 락 +11 / +7 / +9 · 밸런스드 +30 / +34 / +44. 솔버 결정은 타이트한 상대(TAG·락)에게 손해, 루즈한 상대(LAG·밸런스드)에게 약간 이득. 솔버 역산은 스테이션·밸런스드에 이득, TAG·락·LAG 에 손해. 어느 쪽도 전 상대에서 앞서지 못해 **기본값 유지** |
| 어그레서의 플랍 첫 벳(C벳)을 넓게 보기 (기본 55%, 프로파일링 시 실제 C벳 빈도) | 단독 +9.0 → +4.5, 솔버와 합쳐도 -10~-22. `TUNE.cbetAware` 뒤에 남김. C벳 빈도 통계는 남는다 |
| **C벳 디펜스 진단**: TAG 의 헤즈업 C벳은 상위 20% 가 59%, 공기가 41% 인 양극 레인지. AI 는 그 C벳에 66% **레이즈**해 -10.9bb/hand (콜 4%) | 문제는 "너무 접는 것"이 아니라 중간 핸드로 레이즈해 강한 손에 콜당한 뒤 턴·리버에서 계속 잃는 것 |
| 벳 레인지 양극화 (밸류 + 공기 꼬리, U 자 가중치) | C벳에만 적용 +3.0 → +4.2 (잡음 범위), 모든 벳에 적용하면 -3.7. 행동은 안 바뀜(레이즈 54%) — 한 스트리트 EV 는 플랍만 보기 때문 |
| **리버스 임플라이드 오즈**: 플랍·턴에서 레이즈가 콜당하면 지는 쪽 비용에 (1 + rio) 를 곱한다 (4인 20시드) | **채택 rio 1.0**: +4.2 → +14.9 (±3.2), 9인 30시드 +2.0 → +5.2. C벳 레이즈 57% → 21% 로 줄고 레이즈는 승률 0.79 의 강한 손 위주, 콜 13% → 41%. rio 0.6 은 +6.5, 콜에도 0.3 을 주면 +10.4 |
| **상대 성향에 따른 프리플랍 전환** (`adaptiveSolver`): 고급이 프로파일링으로 상대 VPIP 를 30핸드 이상 재서, 레이즈에 직면하면 그 어그레서, 아직 안 열렸으면 뒤에 행동할 상대들의 평균이 기준(4인 28%, 한 명당 -1.8%p, 9인 19%) 이상이면 솔버 표로 결정 | **채택** (없음 → 있음, 4인 20시드 · 9인 30시드): 밸런스드 +30 → **+49** · 9인 +23 → +28, 스테이션 +235 → **+260** · 9인 +261 → +260, LAG +50 → +41 · 9인 +42 → +38 (표준오차 ±6~9 안), TAG +15 → +8 (전환이 결정의 0.6% 뿐이라 카드가 달라진 잡음), 락은 VPIP 7% 라 전환 없음. 전환율: 4인 LAG 93% · 9인 LAG 88% · 9인 밸런스드 79% · TAG 0%. 첫 판은 테이블 전체 평균으로 쟀는데 9인에서 AI 좌석이 평균을 희석해 한 번도 전환되지 않았다 |
| 루즈-어그레시브(LAG) 문: PFR/VPIP 가 기준(4인 0.78, 한 명당 -0.016, 9인 0.70) 이상이면 루즈해도 전환하지 않는다 (`adaptiveAggRatio`). 전환율 LAG 4인 0% · 9인 8%, 밸런스드 97% · 65% | 효과 없음, **기본 꺼 둠**. 문을 달아도 LAG +50 → +43 (9인 +42 → +35), 밸런스드 +30 → +35 (9인 +23 → +29). 비교로 **전환 없이 시드 집합만 바꾸면** LAG 4인 +50 → +44, 9인 +42 → +38 — 전환 뒤에는 첫 전환부터 카드가 달라져 다른 표본이 되므로, LAG 에게 보이던 손해는 이 시드 잡음과 같은 크기였다. 코드와 테스트는 플래그 뒤에 남김 |
| **헤즈업 과다 폴드 진단**: 휴리스틱은 BB 가 BTN 오픈에 66~70% 폴드, BTN 이 3벳에 92~100% 폴드 (솔버 해: 20% / 40%). 사용자 체감이 맞았다 | **채택 `huSolver`**: 헤즈업은 항상 솔버 표로 프리플랍을 결정 (BB 오픈 폴드 20~25%, BTN 3벳 폴드 37~49%). 2인 고급 20시드 × 1000핸드: TAG +20 → +25 · LAG +54 → +58 · 스테이션 +228 → +238 · 락 +41 → +40 · 밸런스드 +16 → +44. 초급은 그대로(이길 수 있어야 하므로) |

튜닝 상수는 `js/ai.js` 의 `TUNE` 에 모여 있어 벤치마크로 바꿔 끼우며 잴 수 있습니다.
상대를 다섯 종류로 늘린 뒤 보이는 것: 솔버 프리플랍은 "누구에게나 좋은" 전략이 아니라 상대에
따라 갈립니다 — 타이트한 상대에겐 넓은 디펜스가 손해, 루즈한 상대에겐 이득. 그래서 고급은
상대 VPIP 를 재서 루즈하다고 확인된 상대에게만 솔버로 전환하고, 헤즈업은 (휴리스틱이 오픈과
3벳에 너무 접어서) 항상 솔버를 씁니다. LAG 에겐 전환해도 이득이 없어 보여 PFR/VPIP 로 LAG 를
걸러내는 문을 달아 봤지만, 그 "손해"는 시드 집합을 바꾸기만 해도 생기는 잡음과 같은 크기라
문은 꺼 두었습니다. 교훈: 전환이 한 번이라도 일어나면 그 뒤 카드가 전부 달라져 다른 표본이
되므로, 이런 비교에는 "같은 설정을 다른 시드로" 잰 잡음 기준선이 꼭 필요합니다.
이 세션에서 가장 큰 개선은 정교한 모델(룩어헤드·솔버)이 아니라 진단 한 줄에서 나왔습니다 —
"C벳에 66% 레이즈, -10.9bb/hand". 한 스트리트 EV 는 플랍 레이즈가 콜당한 뒤의 두 스트리트를
모르므로, 그 손실을 상수 하나(rio)로 넣은 것이 +10bb/100 이었습니다.
룩어헤드가 통하지 않은 이유로 짚이는 것은, 체크/콜 후보에만 미래를 넣고 레이즈 후보의
"콜당한 뒤" 가지는 예전 모델 그대로라 두 후보의 잣대가 달라진 점입니다. 다음 시도는
레이즈 가지에도 같은 모델을 적용하는 것입니다. 단위 테스트에는 큰 퇴행만 잡는 안전망(800핸드
한 시드)이 들어 있습니다. 초기 구현의 수치는 커밋되지 않은 30줄짜리 TAG 로 잰 것이라 지금
봇과 직접 비교할 수 없고, 지금 봇은 팟 오즈로 드로우를 콜하고 C벳을 하는 만큼 더 강합니다.

### 실력이 느는 도구

- **핸드 리뷰** — 내 결정 하나하나를 EV 로 채점합니다.
  "승률 18%, 필요 승률 25% → 폴드가 맞습니다 (-12칩)"
  그 아래 **"왜"** 한 줄이 숫자 뒤의 개념을 짚습니다 — 포지션, 레인지 우위, 팟 오즈와
  임플라이드 오즈, 폴드 에쿼티, 팟 컨트롤, 멀티웨이, 3벳 도미네이션 중 그 자리를 좌우한 하나.
- **생각 정리(코치)** — 코치 모드에서 내 차례에 상단 바의 💡 를 누르면 그 자리의 생각을 정리해 줍니다:
  자리와 포지션, 승률·필요 승률·아웃, "왜" 한 줄, 탄탄한 플레이어의 선택과 선택지별 EV.
  코치를 본 결정은 약점 프로파일에 넣지 않습니다 — 실력이 아니니까요.
- **아웃 카운터** — 보드 위 가능한 모든 홀카드 조합의 강도 분포를 실제로 계산해
  아웃을 셉니다. 보드 페어처럼 "나만 좋아지는 게 아닌" 카드는 자동으로 빠집니다.
- **프리플랍 레인지 차트** — 13×13 격자. 상황(오픈 · 오픈 직면 · 3벳 직면)과 상대 포지션을 고르면
  솔버 빈도를 4색(폴드 · 오픈/레이즈 골드 · 콜 민트 · 3벳 블루)과 혼합 비율 띠로 그리고, 셀을 누르면
  폴드/콜/레이즈 % 팝오버가 뜹니다. 내 핸드의 위치도 표시
- **세션 통계** — VPIP / PFR / AF / 3벳 / WTSD / bb per 100 + 칩 추이 그래프
- **핸드 히스토리와 리플레이** — 미니 테이블(좌석 · 보드 · 팟 · 베팅 · 폴드 · 현재 행동자) 위에서
  스트리트별 타임라인을 누르거나 재생하며 되감고, 그 핸드의 가장 큰 누수 자리로 바로 훈련합니다
- **AI 속마음** — 봇이 왜 그렇게 했는지 (승률 추정, 블러프 여부, 폴드 기대치)
- **스트리트별 액션 요약** — 이번 핸드에서 내가 어떤 라인을 탔는지 한 줄로
- **약점 프로파일** — 리뷰의 결정들을 자리(스트리트 × 상황 12종)와 포지션별로

## AI 는 어떻게 판단하나

**0. 프리플랍 솔버 테이블 — 차트에 쓴다.**
`tools/solve-preflop.js` 가 오프라인에서 푼 프리플랍 게임의 근사해가 `js/preflop-table.js`
(74 KB)에 들어 있습니다. 2·3·6·9인을 따로 풀었고(4~5인은 6인 표, 7~8인은 9인 표),
포지션 × 상황(오픈 · 오픈 직면 · 3벳 직면 · 4벳 직면 · 올인 직면) × 169 클래스마다 콜/레이즈
**빈도**가 있습니다. 프리플랍 차트가 이 빈도를 음영으로 보여줍니다 — "이 포지션에서 이 손은
항상 · 가끔 · 안 연다" 를 한눈에 봅니다.

봇의 결정에는 상대에 따라 씁니다 — 헤즈업(중급·고급)은 항상, 고급은 프로파일링으로 상대가
루즈하다고 확인되면(`TUNE.huSolver` · `TUNE.adaptiveSolver`). 모든 자리에서 켜는 것(`TUNE.solver`)과
상대 레인지 역산(`TUNE.solverRanges`)은 기본이 꺼져 있습니다. 타이트한 상대에게 벤치마크가
나빠졌기 때문입니다 — 아래 튜닝 기록 참고. 솔버가 준 넓은 블라인드 디펜스(BB 가 BTN 오픈에 57% 콜)를
우리 포스트플랍 엔진이 살리지 못하고, 플랍에서 접는 손실만 늘었습니다. 솔버 레인지는 "그
레인지를 제대로 플레이할 수 있는 엔진"을 전제로 하는데 우리 엔진은 아직 거기에 못 미칩니다.
켜면 같은 손으로 어떤 때는 3벳, 어떤 때는 콜하는 혼합 전략이 됩니다.

풀이 방법: 스택 100bb, 오픈 2.5bb(SB 3bb) · 3벳 3배(블라인드 3.5배) · 4벳 2.3배 · 올인의
고정 사이즈, 응답자는 한 명만(누가 콜/3벳하면 뒤는 접는다), 프리플랍이 콜로 끝나면 169×169
올인 승률표(시뮬레이션)에 **실현율**(포지션 · 어그레서 · 핸드 유형별 계수)을 곱해 팟을 나눕니다.
외부 표본 MCCFR(선형 가중) 30만 회, 9인까지 약 1분. 실현율 없이 풀면 BB 가 72o 로도 콜하고
수티드 커넥터는 오픈하지 않는 엉뚱한 해가 나옵니다 — 실현율은 이 추상화가 잃어버린
포지션과 플레이어빌리티를 되돌려 주는 장치입니다. `npm run solve` 로 다시 만들 수 있습니다.

결과 모양: 6인 오픈 UTG 17% · MP 20% · CO 26% · BTN 42% · SB 41%, 9인 UTG 11% ~ BTN 41%,
헤즈업 BTN 75%. BB 는 BTN 오픈에 57% 콜 + 12% 3벳. 프리플랍 차트가 이 빈도를 음영으로 보여줍니다.

**1. 상대 레인지를 역산한다.**
레인지는 169개 핸드 클래스마다 0~1 의 **가중치**입니다. "상위 N%" 밴드 하나로는
같은 백분위의 수티드 커넥터와 약한 오프수트 에이스를 구별할 수 없어서, 액션마다
모양을 다르게 줍니다 — 오픈은 포지션별 상위 14~44% 에 경계를 부드럽게 기울이고,
3벳은 프리미엄에 수티드 에이스·커넥터 블러프가 섞이고, 콜은 포켓페어와 수티드가
앞섭니다. 보드가 깔리면 **가능한 모든 홀카드 조합**(플랍이면 1,081가지)을 실제로
평가해 강도 분포를 만들고, 베팅 사이즈에 따라 그 분포 위에서 가중치를 다시 줍니다.
하드 컷이 아니라 소프트 컷이라 약한 꼬리에 블러프·플로트 몫이 남습니다. 팟의 30% 를
친 상대와 120% 를 친 상대는 다른 레인지입니다. 가중치는 콤보 복제 수로 양자화되어
시뮬레이션 커널은 균등 샘플링 그대로입니다. 내가 든 카드는 상대 콤보에서 빠지므로
블로커 효과가 자동으로 따라옵니다.

**2. 그 레인지로만 승률을 시뮬레이션한다.**
덱에서 아무 카드나 뽑지 않고, 레인지에 속한 조합만 샘플링합니다.

**3. 선택지마다 EV 를 계산해 비교한다.**
폴드·체크·콜, 그리고 여러 베팅 사이즈 각각에 대해:

```
EV(벳 b) = P(전원 폴드) × 팟
         + P(콜) × [ 콜당했을 때의 승률 × (팟 + 콜러수 × b) − (1−승률) × 내 비용 ]
```

폴드 확률은 MDF(최소 방어 빈도)에서 출발해 상대의 실제 폴드 성향으로 보정하고,
**"콜당했을 때의 승률"은 따로 계산합니다** — 상대는 좋은 패로만 콜하니까요.

**4. 블러프는 EV 마진으로 통제한다.**
EV 추정에는 오차가 있으므로, 블러프는 최선의 비블러프 선택지를 일정 마진 이상
이길 때만 실행합니다. 공격적인 성향일수록 마진이 작습니다.

**5. 고급 난이도는 당신을 학습한다.**
포스트플랍 폴드율이 높으면 블러프를 늘리고, 콜이 잦으면 블러프를 끊고 밸류만
칩니다. VPIP 로 당신의 레인지 폭을 보정합니다.

### 개발 중 만난 함정 두 가지

코드 주석에 남겨 두었습니다.

1. **상대 모델링용 레인지를 내 콜 기준으로 재사용하면 안 된다.**
   모델링용 레인지는 넓게 잡는 게 맞지만, 그걸 그대로 콜 기준으로 쓰면
   빅블라인드가 85% 를 디펜스하게 되어 VPIP 가 60% 로 치솟습니다.
2. **프로파일링에 전체 폴드율을 쓰면 안 된다.**
   프리플랍에서 나쁜 패를 접는 것까지 섞여 누구나 70% 안팎이 나오고, 봇이
   "뭐든 접는 상대"로 오판해 블러프를 남발합니다(-69 → +231bb/100).
   블러프가 통할지는 **포스트플랍 폴드율**만이 말해 줍니다.

왜 이렇게 했는지 — 대표적인 오픈 카드 팩(SVG-cards, LGPL-2.1)을 실제로 받아 뜯어보니
카드 한 장의 `<g>` 는 1 KB 남짓인데 전부 `<defs>` 참조라, **4장만 쓰든 52장을 쓰든
938 KB 를 통째로 실어야** 했습니다. `file://` 에서는 외부 SVG `<use>` 가 CORS 로
막히니 HTML 에 인라인해야 하고, 그러면 앱이 392 KB 에서 1.3 MB 로 불어납니다.
게다가 그 팩의 인물 카드 그림은 이 앱의 어두운 화면과 톤이 맞지 않았습니다.

**폰트만 예외입니다.** 타이포그래피는 코드로 그릴 수 없으니까요.
[Pretendard](https://github.com/orioncactus/pretendard) Variable(2.0 MB)에서
앱이 실제로 쓰는 657자만 서브셋해 **114 KB** 로 줄였고, 가변 축을 유지해 파일 하나로
모든 굵기를 씁니다. `@font-face` 의 외부 URL 은 `file://` 에서 CORS 로 차단되므로
`css/font.css` 에 data URI 로 내장했습니다. 라이선스는 SIL OFL 1.1.

참고로 Pretendard 에는 ♠♦♣ 글리프가 아예 없습니다. 무늬를 SVG 로 그린 이유이기도 합니다.

### 핸드 평가기

7장에서 5장을 뽑는 21가지 조합을 모두 평가하는 대신, 랭크 카운트 + 무늬
비트마스크 + 8,192엔트리 스트레이트 룩업 테이블(8KB)로 한 번에 평가합니다.
객체를 전혀 만들지 않아 브루트포스 대비 **64배** 빠릅니다. 독립적인 레퍼런스
구현과 7장 20,000회 점수가 완전히 일치하는지 테스트에서 매번 확인합니다.

커널은 외부 스코프에 의존하지 않도록 작성되어 있어 `toString()` 으로 직렬화해
Web Worker 안에서 그대로 재생성됩니다. 그래서 `file://` 에서도 워커가 뜹니다.

## 배포

GitHub Pages 로 나갑니다. 기본 브랜치에 푸시하면 `.github/workflows/pages.yml`
이 정적 파일만 추려 올립니다. 워크플로는 브랜치 이름을 박아 두지 않고 저장소 설정의
기본 브랜치를 따르므로, 기본 브랜치를 바꿔도 손댈 것이 없습니다. 다른 브랜치의 푸시는
빌드 단계에서 건너뜁니다.

한 가지 장치가 있습니다. 브라우저는 `sw.js` 의 바이트가 달라져야 서비스 워커의
`install` 을 다시 돌립니다. 그런데 `sw.js` 는 배포해도 늘 같은 파일이라, 예전에는
한 번 접속한 사람의 캐시가 첫 방문 때 받은 셸에 영영 멈춰 있었습니다. 고쳐 올려도
남의 화면은 그대로였습니다.

그래서 워크플로가 배포마다 커밋 SHA 를 `sw.js` 에 박습니다.

```yaml
sed -i "s/^const BUILD = 'dev';$/const BUILD = '${GITHUB_SHA}';/" site/sw.js
grep -q "const BUILD = '${GITHUB_SHA}';" site/sw.js || exit 1
```

캐시 이름이 배포마다 달라지므로 셸이 한 벌씩 통째로 갈립니다. 새 `index.html` 과
낡은 `js` 가 섞이지 않고, 옛 캐시는 `activate` 에서 지워집니다. `sed` 가 먹지
않으면 배포를 실패시킵니다 — 조용히 넘어가면 옛 버그가 그대로 돌아오기 때문입니다.

이미 접속했던 사람에게는 **다음 방문에** 새 버전이 뜹니다. 지금 열려 있는 탭을
강제로 새로고침하지는 않습니다 (핸드 중에 화면이 날아가면 곤란하니까요).
